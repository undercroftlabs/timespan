Representing an interval between two dates is only part of the challenge of working with time.

Applications also need to display durations in meaningful ways, preserve intervals between sessions, reconstruct them from external data, and move them through different parts of a system without losing their meaning.

**Timespan 1.3.0 brings those capabilities together.**

Following the public introduction of `@undercroft/timespan` in version 1.1.0 and the correctness improvements of 1.2.0, this release expands what developers can do with a `Timespan` instance.

Version 1.3.0 introduces customizable duration formatting, native JSON serialization and restoration, object-based construction, cloning, and zero-duration detection.

It also addresses additional calendar arithmetic edge cases, improves validation messages, and reorganizes the project to support continued development.

The goal remains the same: provide an intuitive, lightweight, and reliable way to work with time intervals in JavaScript and TypeScript.

## Custom Duration Formatting

One of the most significant additions in version 1.3.0 is the new `format()` method.

Until now, Timespan offered a built-in string representation through `toString()`.

For example:

```typescript
import { Timespan } from '@undercroft/timespan';

const span = Timespan.fromString('2d 4h 30m');

console.log(span.toString());
// "2d 4h 30m"
```

This representation is useful for debugging and displaying compact durations, but applications frequently need more control.

A dashboard might display a duration as `52:30:00`. A scheduling application might show `2 days, 4 hours`. A reporting system might need fixed-width values for consistent output.

Timespan 1.3.0 introduces a formatting system inspired by familiar printf-style directives.

```typescript
const span = Timespan.fromString('2d 4h 30m');

console.log(span.format('%D days, %h hours'));
// "2 days, 4 hours"

console.log(span.format('%H:%02m:%02s'));
// "52:30:00"
```

Formatting is available through both instance and static methods.

```typescript
Timespan.format('%D days', span);
// "2 days"
```

### Total Values vs. Individual Components

The formatting system distinguishes between total elapsed units and individual components of a duration.

**Uppercase specifiers represent totals. Lowercase specifiers represent the components returned by `toTimeframe()`.**

Consider a duration of two days, four hours, and thirty minutes.

```typescript
const span = Timespan.fromString('2d 4h 30m');

console.log(span.format('%H total hours'));
// "52 total hours"

console.log(span.format('%h hour component'));
// "4 hour component"
```

Both values describe the same interval, but they answer different questions.

The complete set of supported specifiers includes:

| Total | Component | Unit         |
| ----- | --------- | ------------ |
| `%Y`  | `%y`      | Years        |
| `%B`  | `%b`      | Months       |
| `%W`  | `%w`      | Weeks        |
| `%D`  | `%d`      | Days         |
| `%H`  | `%h`      | Hours        |
| `%M`  | `%m`      | Minutes      |
| `%S`  | `%s`      | Seconds      |
| `%L`  | `%l`      | Milliseconds |

The additional `%f` specifier formats fractional seconds using the millisecond component.

### Padding, Precision, and Alignment

Formatting directives follow this structure:

`%[flags][width][.precision]specifier`

Supported flags include zero-padding (`0`), left alignment (`-`), explicit positive signs (`+`), and leading spaces.

```typescript
const span = Timespan.fromString('3h 5m 7s');

span.format('%h:%02m:%02s');
// "3:05:07"

span.format('%+H hours');
// "+3 hours"
```

Precision controls the minimum number of digits for integer values.

For `%f`, precision controls how many fractional-second digits are displayed.

```typescript
const span = Timespan.fromMilliseconds(123);

span.format('%f'); // "123"
span.format('%.2f'); // "12"
span.format('%.1f'); // "1"
```

Fractional digits are truncated rather than rounded.

A literal percent sign can be included using `%%`.

To prevent excessively large formatting allocations, widths and precisions of 1,000,000 or greater are rejected. The format string itself has no fixed length limit.

This provides flexibility while retaining explicit validation of formatting directives.

## Saving and Restoring Timespans with JSON

Another major addition in version 1.3.0 is native JSON serialization.

In many applications, an interval needs to exist beyond the lifetime of the JavaScript object that originally represented it.

It might be stored in browser storage, transmitted between services, included in a configuration file, or saved as part of an application's state.

Timespan now provides a consistent way to serialize and reconstruct intervals.

### A Portable JSON Representation

Every Timespan can be represented using a compact object containing its type and endpoints.

```typescript
import { Timespan } from '@undercroft/timespan';

const span = new Timespan(
  new Date('2026-11-15T09:00:00Z'),
  new Date('2026-11-15T17:00:00Z'),
);

const json = span.toJSON();

console.log(json);
```

The resulting object has this structure:

```json
{
  "$type": "Timespan",
  "start": "2026-11-15T09:00:00.000Z",
  "end": "2026-11-15T17:00:00.000Z"
}
```

The `$type` discriminator identifies the serialized value as a Timespan, while `start` and `end` preserve the exact endpoints as ISO 8601 strings.

The corresponding TypeScript type, `TimespanJson`, is exported from the package.

### Integration with JSON.stringify

JavaScript automatically calls an object's `toJSON()` method when serializing it with `JSON.stringify()`.

Timespan takes advantage of this built-in behavior.

```typescript
const serialized = JSON.stringify(span);
```

A convenience method is also available:

```typescript
const serialized = Timespan.stringify(span);
```

Both produce the same JSON representation.

### Reconstructing a Timespan

The `fromJSON()` method accepts the serialized object and reconstructs a new Timespan instance.

```typescript
const original = Timespan.fromHours(8);

const json = original.toJSON();

const restored = Timespan.fromJSON(json);

console.log(restored.equals(original, 'range'));
// true
```

For JSON strings, `Timespan.parse()` provides a direct alternative.

```typescript
const serialized = Timespan.stringify(original);

const restored = Timespan.parse(serialized);
```

Unlike a generic JSON parser, `Timespan.parse()` expects its root value to be a single serialized Timespan. It does not automatically traverse arbitrary nested objects or arrays.

### Restoring Nested Timespans

Applications often need to serialize more than one value at a time.

For example, a larger object might contain configuration data alongside a Timespan.

Version 1.3.0 introduces `Timespan.reviver`, which integrates with the native JSON parser.

```typescript
const session = {
  name: 'Maintenance Window',
  scheduled: Timespan.fromHours(4),
};

const serialized = JSON.stringify(session);

const restored = JSON.parse(serialized, Timespan.reviver);

console.log(restored.scheduled instanceof Timespan);
// true
```

The reviver recognizes serialized Timespan objects and reconstructs them while leaving unrelated values unchanged.

This allows Timespan instances to be embedded in larger JSON documents without requiring developers to manually reconstruct every nested interval.

### Validating Serialized Data

The new `isTimespanJSON()` method checks whether an unknown value matches the expected serialized structure.

```typescript
const json = span.toJSON();

console.log(Timespan.isTimespanJSON(json));
// true

console.log(Timespan.isTimespanJSON(span));
// false
```

It's important to distinguish structural validation from successful reconstruction.

`isTimespanJSON()` verifies that the `$type` discriminator is correct and that `start` and `end` are strings. It does not establish that those strings contain valid dates or that the resulting interval has valid endpoints.

`fromJSON()` performs the additional validation required to reconstruct a Timespan.

This separation makes it possible to inspect unknown JSON values without confusing a structural type check with full data validation.

## Constructing Timespans from Objects

Version 1.3.0 also introduces `Timespan.fromObject()`, a convenient alternative to constructing durations from strings or individual units.

Previously, developers could create intervals using methods such as `fromString()`, `fromHours()`, and `fromUnits()`.

The new method accepts an object containing any combination of supported timeframe components.

```typescript
const span = Timespan.fromObject({
  days: 3,
  hours: 4,
  minutes: 30,
});

console.log(span.toString());
// "3d 4h 30m"
```

The method accepts a partial timeframe, so developers only need to specify the units they intend to use.

Omitted and zero-valued components are skipped.

### Working with a Specific Start Date

As with the existing factory methods, developers can provide an optional starting date.

```typescript
const start = new Date('2026-11-15T09:00:00Z');

const span = Timespan.fromObject(
  {
    weeks: 2,
    days: 3,
    hours: 6,
  },
  start,
);
```

The specified units are applied in a consistent order, from years down to milliseconds.

Month and year calculations use the same calendar-aware converters as `fromMonths()` and `fromYears()`, including end-of-month clamping.

This makes object-based construction particularly useful when duration values come from form inputs, configuration objects, or structured application data.

Instead of manually assembling a duration string, developers can pass the values directly.

## Cloning and Zero-Duration Detection

Two smaller additions in this release make Timespan instances easier to work with in application code.

### Creating Independent Copies with clone()

The new `clone()` method creates a separate Timespan with the same starting and ending dates.

```typescript
const original = Timespan.fromDays(7);

const copy = original.clone();

console.log(copy === original);
// false

console.log(copy.equals(original, 'range'));
// true
```

The copied Timespan preserves the original interval but does not share its internal `Date` objects.

A static equivalent is also available.

```typescript
const copy = Timespan.clone(original);
```

This builds on the defensive copying improvements introduced in version 1.2.0.

### Identifying Zero-Length Intervals

Timespan permits intervals whose starting and ending instants are identical.

Version 1.3.0 introduces `isZero()` to identify these cases explicitly.

```typescript
const date = new Date('2026-11-15T12:00:00Z');

const span = new Timespan(date, date);

console.log(span.isZero());
// true

console.log(span.toMilliseconds());
// 0

console.log(span.toString());
// ""
```

The method returns `true` when the interval's duration is zero milliseconds.

A static version is also available:

```typescript
Timespan.isZero(span); // true
```

This is useful when applications need to distinguish an empty interval from an interval containing elapsed time.

## Continued Improvements to Calendar Arithmetic

Version 1.2.0 introduced important corrections to month and year calculations, including anniversary-based counting and end-of-month clamping.

Version 1.3.0 builds on those improvements by correcting how duration breakdowns are calculated after a clamped calendar anniversary.

Consider an interval starting on January 31 and extending into February.

Because February has fewer days, advancing one calendar month requires special handling.

Earlier calculations could correctly clamp the resulting date but encounter problems when calculating the remaining days, hours, or other components.

The internal breakdown calculation previously advanced dates using native operations such as `setUTCMonth()` or `setUTCFullYear()`.

Under certain conditions, these operations could roll dates into an unintended month and produce an incorrect remainder.

Version 1.3.0 instead measures the remainder from the properly clamped anniversary.

This affects both:

- `toTimeframe()`, which returns the individual components of an interval.
- `toString()`, which formats those components using Timespan's standard compact representation.

The release also improves handling of Gregorian month lengths, including February in leap years.

Additional safeguards prevent calculations from counting month or year anniversaries that fall outside JavaScript's representable date range.

These changes are particularly important for calendar-based durations near the ends of months, leap days, and the boundaries of valid JavaScript dates.

Ordinary successful date calculations retain their established behavior.

## Clearer Validation and Error Reporting

Reliable libraries need to explain why an operation fails, not merely indicate that something went wrong.

Version 1.3.0 improves validation messages throughout the public API.

For example, invalid dates now produce:

`Invalid date: expected a valid Date.`

Reversed date ranges report:

`Invalid date range: expected the start date to be less than or equal to the end date.`

Unsupported time units produce:

`Invalid time unit: expected a recognized time unit.`

The duration string parser also provides more specific messages for disallowed characters and excessive input length.

This helps applications provide clearer feedback and makes it easier for developers to identify invalid inputs.

### Safer Numeric Input

Unit-based factory methods now explicitly reject non-finite numeric values and amounts that would produce dates outside JavaScript's representable range.

Negative amounts remain invalid.

Fractions of fixed-length units continue to be supported.

```typescript
const span = Timespan.fromHours(1.5);

console.log(span.toMinutes());
// 90
```

These validations help distinguish legitimate fractional durations from values that cannot represent a valid interval.

Developers relying on exact error message text should review their error handling when upgrading.

## A Modernized Project Architecture

Beyond the new public APIs, version 1.3.0 represents a significant change in how Timespan is developed and maintained.

The repository was reorganized into a **pnpm workspace**, with the core library located under `packages/timespan`.

This separates the publishable package from repository-level tooling and external distribution tests.

Although consumers continue installing the same `@undercroft/timespan` package, the new structure provides a more flexible foundation for future development.

### Updated Build and Test Infrastructure

The development toolchain now uses several modern tools:

- **pnpm:** Workspace and dependency management.
- **tsdown:** Building the distributed library.
- **Vitest:** Unit testing, coverage, and benchmarking.
- **oxlint and oxfmt:** Linting and formatting.
- **Playwright:** Browser testing against the generated bundles.

The project also introduces benchmark files alongside implementation and test files, making it possible to measure performance and evaluate future changes.

This creates a more systematic process for improving the library without introducing unnecessary overhead.

### Stronger Package Verification

A library's source code is only part of what its consumers receive.

The distributed npm package must also expose the correct entry points, include usable type declarations, and function in the environments it supports.

Version 1.3.0 strengthens distribution verification with tooling that inspects the package as a consumer would receive it.

The verification process includes package metadata checks, TypeScript declaration compatibility, bundle loading, and inspection of the generated npm package.

The package also introduces an explicit `exports` map.

This directs modern `import` statements to the ESM distribution, `require()` calls to the CommonJS distribution, and the dedicated `@undercroft/timespan/umd` subpath to the browser build.

The existing `window.Timespan` browser global remains available.

Other internal package paths are not publicly exported.

Together, these improvements make the public package boundary more explicit and help prevent publishing problems that source-level tests alone might not detect.

## Improved Documentation and Interactive Examples

Version 1.3.0 also introduces a more practical approach to documentation.

Rather than relying exclusively on API descriptions, the README is organized around common developer tasks.

These include creating intervals, parsing and formatting durations, comparing timespans, converting units, saving and restoring JSON, and copying existing instances.

Each task includes a working example alongside a CodePen playground and preview.

This gives developers an opportunity to experiment with the library without first setting up a project locally.

The release documentation also includes version-specific size information.

At the time of the 1.3.0 release, the documented ESM bundle size was approximately **3.8 kB Brotli-compressed**, with zero runtime dependencies.

The install-size badge separately reports the unpacked package size.

These measurements are tied to the 1.3.0 distribution rather than changing whenever a newer version is published.

## Upgrading to 1.3.0

Existing applications can upgrade through npm:

```shell
npm install @undercroft/timespan@1.3.0
```

Version 1.3.0 retains the established Timespan APIs while introducing additional methods and improving input validation.

Most applications using the public package interface should not require substantial changes.

However, developers should review a few compatibility considerations.

**Validation messages have changed.** Applications matching the exact text of thrown errors may need adjustments.

**Package exports are now explicit.** Applications should continue importing from `@undercroft/timespan` rather than using internal module paths.

**Calendar breakdowns are more accurate.** Intervals involving clamped month or year anniversaries may produce corrected values from `toTimeframe()` and `toString()`.

**Factory input validation is stricter.** Non-finite numbers and amounts that produce unrepresentable dates now fail explicitly.

These changes help maintain a more consistent and predictable API.

## Moving Beyond Basic Duration Calculations

The first public Timespan release established a convenient interface for creating and measuring time intervals.

Version 1.2.0 strengthened that foundation with comparison methods and improved calendar correctness.

**Version 1.3.0 makes those intervals more useful throughout an application.**

Custom formatting makes durations easier to present. JSON serialization allows intervals to survive beyond their original JavaScript objects. Object-based construction simplifies integration with structured data, while cloning and zero-duration detection round out the public API.

The internal improvements are just as important.

More rigorous validation, improved calendar calculations, browser testing, benchmarking, and package verification establish a foundation for continued development.

Timespan is evolving from a convenient date utility into a more complete library for working with time intervals across the JavaScript ecosystem.

And there's still much more to explore.
