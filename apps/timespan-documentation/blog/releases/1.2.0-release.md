Working with time is deceptively complicated.

A day might seem like a fixed interval, but months have different lengths, leap years introduce exceptions, and crossing a calendar boundary doesn't necessarily mean an entire month or year has elapsed.

Even seemingly straightforward operations, such as comparing two durations or parsing a string into a time interval, require careful handling to produce reliable results.

**Timespan 1.2.0 focuses on getting those details right.**

Following the initial public release of `@undercroft/timespan` in April 2025, version 1.2.0 introduces new comparison methods, strengthens duration parsing, corrects important calendar calculations, and expands automated testing across multiple JavaScript environments.

Rather than introducing new time units or formatting conventions, this release concentrates on correctness, consistency, and developer confidence.

## Comparing Timespans

One of the most significant additions in version 1.2.0 is the ability to compare two `Timespan` instances directly.

The release introduces two methods:

- **`equals()`** determines whether two timespans represent the same duration or the same date range.
- **`compareTo()`** determines whether one timespan is shorter than, equal to, or longer than another.

Both methods are available as instance methods and static methods.

### Comparing Durations with equals()

By default, `equals()` compares timespans according to their total elapsed duration.

```typescript
import { Timespan } from '@undercroft/timespan';

const oneDay = Timespan.fromHours(24);
const anotherDay = Timespan.fromDays(1);

console.log(oneDay.equals(anotherDay)); // true
```

Although these timespans were created using different units, each represents 24 hours of elapsed time.

This provides a convenient way to determine whether two durations are equivalent without manually converting them to a common unit.

The method also supports a static form:

```typescript
const equal = Timespan.equals(oneDay, anotherDay);

console.log(equal); // true
```

### Comparing Date Ranges

Equal durations don't necessarily represent the same interval.

For example, two appointments might each last one hour but occur on different dates.

Timespan supports this distinction through the optional `'range'` comparison mode.

```typescript
const morning = new Timespan(
  new Date('2026-11-04T09:00:00Z'),
  new Date('2026-11-04T10:00:00Z'),
);

const afternoon = new Timespan(
  new Date('2026-11-04T14:00:00Z'),
  new Date('2026-11-04T15:00:00Z'),
);

console.log(morning.equals(afternoon)); // true

console.log(morning.equals(afternoon, 'range')); // false
```

By default, the comparison returns `true` because both intervals last one hour.

When `'range'` is specified, Timespan compares their exact starting and ending instants instead.

This distinction is useful when working with schedules, reservations, activity records, and other applications where the position of an interval matters as much as its duration.

### Ordering Timespans with compareTo()

The new `compareTo()` method makes it possible to order timespans by their elapsed duration.

```typescript
const shortSpan = Timespan.fromHours(6);
const longSpan = Timespan.fromHours(12);

console.log(shortSpan.compareTo(longSpan)); // -1
console.log(longSpan.compareTo(shortSpan)); // 1
console.log(shortSpan.compareTo(shortSpan)); // 0
```

The return value follows a familiar comparison convention:

- `-1` when the first timespan is shorter.
- `0` when the durations are equal.
- `1` when the first timespan is longer.

The method can also be used directly with JavaScript's sorting functions.

```typescript
const spans = [
  Timespan.fromHours(12),
  Timespan.fromHours(3),
  Timespan.fromHours(8),
];

spans.sort((a, b) => a.compareTo(b));

console.log(spans.map((span) => span.toHours()));
// [3, 8, 12]
```

A static equivalent is also available:

```typescript
Timespan.compareTo(shortSpan, longSpan);
```

Together, `equals()` and `compareTo()` establish a foundation for applications that need to compare, organize, or evaluate time intervals.

## More Accurate Calendar Calculations

One of the most important areas of improvement in version 1.2.0 is calendar arithmetic.

Unlike seconds or minutes, months and years cannot always be treated as fixed-length intervals.

The number of days in a month varies, and leap years make year-based calculations more complicated.

Timespan now handles several of these cases more consistently.

### Counting Completed Years

Consider an interval beginning on December 31 and ending on January 1.

Although the calendar year has changed, only one day has elapsed.

```typescript
const span = new Timespan(
  new Date('2022-12-31T00:00:00Z'),
  new Date('2023-01-01T00:00:00Z'),
);

console.log(span.toDays()); // 1
console.log(span.toYears()); // 0
```

Earlier calculations could incorrectly count a year by subtracting calendar year values.

Version 1.2.0 instead considers whether the appropriate anniversary has actually been reached.

This distinction also applies when an interval spans nearly an entire year.

```typescript
const span = new Timespan(
  new Date('2022-06-15T00:00:00Z'),
  new Date('2023-06-14T00:00:00Z'),
);

console.log(span.toYears()); // 0
```

A complete year has not elapsed until the anniversary is reached.

### Counting Completed Months

Month calculations now account for the time of day as well as the calendar date.

Consider an interval beginning at noon on January 15 and ending at 11:00 AM on February 15.

```typescript
const span = new Timespan(
  new Date('2023-01-15T12:00:00Z'),
  new Date('2023-02-15T11:00:00Z'),
);

console.log(span.toMonths()); // 0
```

Although the dates fall on the same day of consecutive months, the interval is still one hour short of a complete calendar month.

The updated calculation recognizes that difference.

### Handling the End of a Month

Another important improvement concerns adding months to dates near the end of a calendar month.

What should happen when an application adds one month to January 31?

JavaScript's native date operations can overflow into March when the target month doesn't contain the requested day.

Timespan 1.2.0 instead clamps the resulting date to the last valid day of the target month.

```typescript
const start = new Date('2023-01-31T00:00:00Z');

const span = Timespan.fromMonths(1, start);

console.log(span.end.toISOString());
// 2023-02-28T00:00:00.000Z
```

Leap years are handled appropriately.

```typescript
const start = new Date('2024-01-31T00:00:00Z');

const span = Timespan.fromMonths(1, start);

console.log(span.end.toISOString());
// 2024-02-29T00:00:00.000Z
```

The same behavior applies when adding years from February 29 into a non-leap year.

```typescript
const start = new Date('2020-02-29T00:00:00Z');

const span = Timespan.fromYears(1, start);

console.log(span.end.toISOString());
// 2021-02-28T00:00:00.000Z
```

Importantly, duration-string parsing now uses the same underlying unit converters as the factory methods.

For example, `Timespan.fromString('1M', start)` and `Timespan.fromMonths(1, start)` follow the same calendar addition rules.

This eliminates inconsistencies between different ways of constructing an interval.

## More Reliable Duration Parsing

Duration strings provide a convenient way to create timespans, but malformed input should never produce an unexpected or misleading result.

Version 1.2.0 strengthens the `fromString()` parser by enforcing clearer input rules and eliminating several edge cases.

### Invalid Input Now Produces an Error

Previously, certain malformed inputs could be partially matched and produce an unintended zero-length interval.

Examples included unusually long numeric values and unit names without a corresponding number.

These inputs now fail explicitly.

```typescript
Timespan.fromString('99999999999ms'); // Throws
Timespan.fromString('h'); // Throws
```

The parser also validates that the entire input has been consumed rather than accepting only the portions that happen to match.

### Duplicate Units Are Rejected

A duration string should not silently overwrite an earlier value when the same unit appears more than once.

```typescript
Timespan.fromString('1h 30m'); // Valid

Timespan.fromString('1h 2h'); // Throws
```

Repeated units now produce a `Duplicate date unit` error.

This includes repetitions using different aliases for the same unit.

```typescript
Timespan.fromString('1h 2hours'); // Throws
```

By detecting these mistakes immediately, applications can surface meaningful validation feedback instead of processing an unintended duration.

### Fractional Values Remain Restricted

The string parser continues to require integer values for each duration component.

```typescript
Timespan.fromString('1.5h'); // Throws
```

For fractional quantities of fixed-length units, developers can use the appropriate factory method instead.

```typescript
const span = Timespan.fromHours(1.5);

console.log(span.toMinutes()); // 90
```

This keeps the string parser's rules explicit while preserving flexibility through the programmatic API.

### Parsing State Is Isolated Between Calls

Version 1.2.0 also resolves a less visible issue involving JavaScript regular expressions.

Global regular expressions maintain an internal `lastIndex` property that tracks the position of the next match.

If a parsing operation throws before resetting that state, subsequent calls can behave unexpectedly.

Timespan now creates an independent regular expression for each parsing operation.

As a result, a failed parse no longer interferes with future requests.

```typescript
const start = new Date('2026-11-04T00:00:00Z');

Timespan.fromString('1h', start); // Valid

try {
  Timespan.fromString('1h 2x', start);
} catch {
  // Handle the invalid duration.
}

const span = Timespan.fromString('3d', start);

console.log(span.toDays()); // 3
```

A validation failure is now isolated to the operation that caused it.

## Protecting Timespan's Internal State

Version 1.2.0 also improves how Timespan protects the dates and duration information it stores.

JavaScript's `Date` objects are mutable. Even a property marked `readonly` in TypeScript can still reference an object whose internal value can change.

That creates a subtle problem when a library stores an externally supplied date or returns a reference to its internal state.

Timespan now copies the input dates when constructing an interval and returns independent values from its `start`, `end`, and `toTimeframe()` accessors.

For example:

```typescript
const span = Timespan.fromHours(2);

const start = span.start;

// Modify the returned Date.
start.setUTCFullYear(2035);

// The stored start date remains unchanged.
console.log(span.start.getUTCFullYear() === 2035);
// false
```

The same protection applies to the duration breakdown.

```typescript
const span = Timespan.fromHours(2);

const timeframe = span.toTimeframe();

timeframe.hours = 999;

console.log(span.toTimeframe().hours); // 2
```

These changes help ensure that a `Timespan` instance remains internally consistent after construction.

They are particularly valuable when timespans are passed between functions, shared across components, or used within larger application state models.

## Expanded Browser Testing

Another major improvement in version 1.2.0 is the introduction of automated browser distribution testing.

The original 1.1.0 release introduced a UMD build, allowing Timespan to run directly in a browser.

Version 1.2.0 takes that support further by verifying the actual generated distributions using **Playwright**.

The browser test suite covers:

- Chromium
- Firefox
- WebKit

Both UMD and ESM distributions are tested.

The tests load compiled JavaScript from the `dist` directory rather than importing the original TypeScript source code.

This is an important distinction.

A library may pass every unit test against its source code while still producing a distribution that fails to load or behaves differently in a consumer's environment.

Testing the compiled output helps catch problems involving bundling, exports, browser compatibility, and distribution packaging.

The project also provides commands for running these tests locally.

```shell
npm run test:browser
```

For development environments where native browser dependencies are difficult to install, container-based browser testing is also supported.

This provides another layer of confidence that the published library works in the environments it claims to support.

## Development and Distribution Improvements

Version 1.2.0 includes additional work to modernize the development environment and strengthen the release process.

The toolchain was updated to newer versions of its core development dependencies, including:

- TypeScript 6
- Jest 30
- ESLint 10
- Husky 9

The release also updates the package's repository metadata to reference its home under the Undercroft Labs GitHub organization.

The supported Node.js engine configuration targets versions 22, 24, and 26.

Bundle size monitoring remains part of the project, with the Brotli-compressed JavaScript size budget increased from 3.5 KB to 4 KB.

The project also documents its testing and publishing procedures, including the browser-testing workflow and npm Trusted Publishing.

These improvements are largely invisible to applications consuming Timespan, but they strengthen the processes used to build, test, and distribute the library.

## Upgrading to 1.2.0

Existing applications using the public Timespan API can upgrade through npm:

```shell
npm install @undercroft/timespan@1.2.0
```

The release retains the established construction, parsing, formatting, and conversion APIs.

However, applications should be aware of the stricter parser behavior and corrected calendar calculations.

Malformed duration strings that previously produced results may now throw errors, and month- or year-based calculations may produce different, more accurate results in edge cases.

These changes are intentional.

The goal is to prevent ambiguous input and calendar arithmetic from silently producing misleading values.

Applications relying on the previous behavior should review their date-handling and validation logic when upgrading.

## Building Confidence in Time Calculations

Timespan 1.2.0 isn't primarily about expanding the number of things the library can do.

It's about making the things it already does more dependable.

The new comparison methods simplify common duration operations. Improved calendar arithmetic handles important real-world edge cases. Stronger parsing rules reject invalid input rather than silently accepting it, while defensive copying protects the consistency of stored intervals.

Combined with expanded browser testing, these changes establish a stronger foundation for future development.

Time calculations are an essential part of many applications, and reliability matters just as much as convenience.

**Timespan 1.2.0 is another step toward providing both.**
